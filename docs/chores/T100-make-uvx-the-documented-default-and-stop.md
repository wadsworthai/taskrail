# T100 — Make uvx the documented default and stop assuming a global install

Kind: chore · Epic: E05 · Status: scoped

## Goal

The no-global-install route already works: the committed wrapper falls back to
`uvx --from git+<repo>@<pin>`, and the generated GitHub workflow installs nothing but `uv`. The
documentation does not say so — `README.md` *Install* and `DESIGN.md` §9 both open with
`uv tool install`, and *Use* shows bare `taskrail <command>`, which only works with a global
install. Document both routes with **uvx as the recommended one**, so a reader's default is a
repository that pins a version and calls it through `.taskrail/bin/taskrail`, with nothing
installed on the machine.

## Grounding: what is true today

Measured on this branch (base `origin/main`, `d6fc5f7`).

**The wrapper's uvx fallback** — `.taskrail/bin/taskrail:17–32` (generated by
`src/taskrail/install.py:237–252`): with `TASKRAIL_BIN` unset and a non-`local:` pin, it uses an
installed `taskrail` only when `v$(taskrail --version)` equals the pin, and otherwise
`exec uvx --quiet --from "git+${TASKRAIL_SOURCE:-https://github.com/wadsworthai/taskrail.git}@$pin" taskrail "$@"`.
With neither, it exits 2 naming `uv` (`:28–31`).

**The whole route, run with `taskrail` absent from `PATH`.** A scratch repository, a `PATH` of
`<scratch>/nobin:/usr/bin:/bin` holding only symlinks to `uv` and `uvx`, and the tag `v0.3.0`:

```
$ echo "taskrail on PATH? $(command -v taskrail || echo NO)"
taskrail on PATH? NO
$ uvx --quiet --from "git+file:///thezone/…/taskrail@v0.3.0" taskrail init --integration claude
created   .taskrail/config.toml
created   TODO.md
created   .taskrail/bin/taskrail
created   .claude/skills/taskrail/SKILL.md
…
note      skills changed: restart the agent session so it loads them
0 file(s) already up to date
$ head -1 .taskrail/config.toml
version = "v0.3.0"
$ ./.taskrail/bin/taskrail --version
taskrail 0.3.0
$ ./.taskrail/bin/taskrail validate
history: not checked (no commits)
0 task(s) in 1 backlog(s): 0 error(s), 0 warning(s)
```

So bootstrapping with `uvx --from git+<repo>@<tag> taskrail init` works, **and `init` pins the
version it ran as** (`src/taskrail/install.py:414`, `default_config`), so the wrapper afterwards
reproduces exactly the taskrail that wrote the repository. The prerequisite is `uv` alone.

**What `init` prints.** The report is `created`/`updated`/`removed`/`skipped`/`note` lines plus a
count (`src/taskrail/install.py:60–67`). Its only notes are "skills changed: restart the agent
session so it loads them" (`:449`), "no agent integration installed; pass --integration claude or
--integration opencode" (`:451`), the kind-filter notes (`:429`, `:431`) and "not a git repository"
(`:409`). **None of them mentions installing, upgrading or calling a global `taskrail`.** The run
above is the whole output. See decision 3.

**`taskrail self upgrade`** runs `uv tool install --force taskrail --from git+<source>@<tag>`
(`src/taskrail/install.py:497`) — it replaces a CLI on the machine and never touches
`.taskrail/config.toml`. For a repository that never installed one it is a no-op at best. There,
upgrading is moving the pin: `taskrail upgrade` re-installs the skills for the running CLI and
sets `version` to it (`:475–482`, `set_version_pin` at `:459–472`), so
`uvx --from git+<repo>@<newtag> taskrail upgrade` is the one-command upgrade. To be confirmed by
running it at implement.

**The generated workflow** (`src/taskrail/install.py`, `workflow()`) is `actions/checkout@v7` with
`fetch-depth: 0`, `astral-sh/setup-uv@v10`, then `.taskrail/bin/taskrail validate` — it never
installs taskrail, which is the uvx route already in use and undocumented.

**Nothing under test depends on this prose.** No test reads `README.md` or `DESIGN.md` §9;
`tests/test_install.py:283` asserts the `self upgrade` *command*, which this task does not change.

## Decisions needed (at the scope gate)

**1. How far "everything oriented to uvx" reaches in README's *Use*.** The block shows ~30 bare
`taskrail <command>` lines, which work only with a global install.
**Recommended: one sentence above the block, examples left short.** Something like: *"A repository
calls taskrail through the wrapper `init` commits — `.taskrail/bin/taskrail <command>`. The
examples below are written short so they fit; with the CLI installed on your machine they work as
typed."* It states the default once, where the reader meets the block, and keeps ~30 lines of
aligned comments readable — several are already near the column width, and a 22-character prefix on
each would push the comments off or force a re-wrap of the whole block.
*Alternative (a):* rewrite every line to `.taskrail/bin/taskrail …` — maximally honest, but the
block becomes hard to scan and the diff touches every line of the section for no new information.
*Alternative (b):* rewrite only the first two or three lines and note the rest are abbreviated —
mixes two spellings inside one block, which reads like an oversight.

**2. What the documentation says about `taskrail self upgrade`, and where.**
**Recommended: both places, each saying the part its reader needs.** In `README.md` *Install*, a
short "Upgrading" paragraph on the uvx route — `uvx --from "git+…@vX.Y.Z" taskrail upgrade` moves
the pin and re-installs the skills — plus the corrected one-line comment on `self upgrade` in
*Use*; in `DESIGN.md` §9, one clause on the existing `self upgrade` sentence saying that for a
repository with no global install, upgrading is changing the pin. The reader who never installs
a CLI meets the question in the README, and §9 is where the two commands are already contrasted.
*Alternative (a):* §9 only — leaves the README recommending a route whose upgrade path it never
states. *Alternative (b):* README only — §9's sentence then stays half-true for the route §9 would
be recommending. *Alternative (c):* deprecate or hide `self upgrade` — **not recommended**, out of
scope: it is a working command for the install route this task explicitly keeps, and
`tests/test_install.py:283` pins its behaviour.

**3. Does `init`'s report need a word, i.e. does `src/taskrail/install.py` change?**
**Recommended: no — leave `install.py` alone.** The full report of a real bootstrap run is quoted
above; the only note is the agent-restart one, and nothing in `Report.format` or the note list
assumes, mentions or suggests a global install. The task made this change conditional ("if it says
anything that assumes a global install"), and it does not.
*Alternative:* add a note pointing the reader at `.taskrail/bin/taskrail` after a first `init`.
Tempting, but it is new behaviour rather than a correction, it would print on every first install
including the global-install route, and `tests/test_install.py` would need a new assertion — a
separate task if it is wanted.

**4. May `CHANGELOG.md`'s header block change too?** Lines 3–7, above `## Unreleased`, are the
other place that teaches only `uv tool install`:
*"Releases are tagged `vX.Y.Z`. Install one with: `uv tool install taskrail --from "git+…@vX.Y.Z"`"*.
My touch map allows `CHANGELOG.md` only under `## Unreleased`, so I am asking rather than editing.
**Recommended: yes, include it** — two lines, changing the command to the `uvx … taskrail upgrade`
form with `uv tool install` named as the alternative; leaving it makes the changelog contradict the
README it sits beside. *Alternative:* leave it and open a follow-up; the contradiction then ships.

**5. May README's *Releasing* step 3 change?** It reads *"Verify a clean install from the tag"*,
which on the new default should be verified on both routes.
**Recommended: yes, four words** — *"Verify a clean install from the tag, on both routes"* (or
equivalent), so the release checklist covers the one this task makes the default. *Alternative:*
leave it; the step is already vague enough not to be wrong, and the follow-up test in decision 6
would cover it mechanically.

**6. Should I open the follow-up test task?** The task says a test that exercises `init` and the
wrapper with `taskrail` absent from `PATH` is out of scope here, and to propose it if the work
shows it is needed. **The work shows it is needed**: the route is now the *documented default*, it
is exercised by nothing in `tests/`, and the run above had to be done by hand with a purpose-built
`PATH`. **Recommended: open one chore in E05**, roughly *"Test `init` and the wrapper with taskrail
absent from PATH"*, 2 points, no dependencies. *Alternative:* do not open it and note it here only.
