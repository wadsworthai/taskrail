# T104 — State in the core skill that `show --fetch` needs `branch_record_remote`

## Goal

Step 3 of `src/taskrail/skills/taskrail/SKILL.md` tells every executor, in every consuming
repository, to run `taskrail show <ID> --json --fetch` before it cuts the task's branch. The
condition on that flag is already in the sentence — *"when the repository mirrors them"* — but it
sits mid-sentence between two em dashes in the longest step of the skill, so the step reads as
though the fetch always does something.

[T097](../spikes/T097-record-whether-any-repository-enables-th.md) measured both halves and put
three questions to the human, who answered **1 B, 2 B, 3 C** on 2026-09-18: no repository visible
to them sets either remote key, **nothing is retired**, and the `--fetch` step **stays** — with
the condition said plainly instead of implied.

This chore is that one clause. It changes no behaviour, no flag, no output and no code: the
`--fetch` flag, `_fetch_records` and `[git].branch_record_remote` are all untouched.

## What T097 measured, re-verified here

(`/thezone/shared/repositories/utils/taskrail/.worktrees/T104-state-in-the-core-skill-that-show-fetch`)

```
real  0m0.255s          # against 1.561s for a real `git fetch origin`, measured in T097 V4
```

Byte-identical output, exit 0, no message, no network. The guard is the reason:

```
$ sed -n '64,69p' src/taskrail/cli.py
def _fetch_records(project: Project) -> None:
    """Bring mirrored branch records into this clone before any branch is resolved; a failure only warns (§6.4)."""
    config = project.config
    if not config.branch_record_remote:
        return
    _, error = branches.fetch(config)
```

**And load-bearing when the key is set.** T097 *V7* took this from
`tests/test_branch_records_remote.py`, whose `mirrored` fixture clones a real bare origin with
`branch_record_remote = "origin"`: without `--fetch`, `show` reports a task finished on a branch
renamed in another clone as `pending` with a `template` branch name, and `next` drops its
dependent from the eligible list entirely. Those two facts are what the new wording has to carry,
and they are why route B — dropping the flag — was recommended against and not taken.

Applied, replacing lines 64–68 (now 64–71):

```
   the mainline's own remote that `show` reported, then `taskrail show <ID> --json --fetch`. The
   `--fetch` does nothing, and says nothing, unless the repository sets
   `[git].branch_record_remote`; where it is set, it brings in the branch names other clones
   recorded, without which a task finished on a branch renamed in another clone reads here as
   pending on a template name. Take `show`'s `base.onto` as the ref to branch from — the local or
   the remote mainline, whichever is further ahead, or, when `base.dependency` names a dependency
   finished only on its unmerged branch, that branch. If `base.diverged` is true, stop and ask
   which one to use; …
```

The gate accepted the wording with one correction, applied above: the fifth sentence was proposed
as *"That `show`'s `base.onto` is the ref to branch from"* — a fragment left over from splitting
the original em-dash sentence — and is now the imperative **"Take `show`'s `base.onto` as the ref
to branch from"**, which matches the voice of the rest of the step. The whole step was read back
after the edit.

Five lines become eight: the clause itself takes three more, and the sentence that follows it
(`If `base.diverged` is true, …`) rewraps across the boundary my text no longer ends at. Every
line stays inside the file's 98-column wrap; the shortest, at 49 characters, is the tail of that
rewrap, and the step already carries shorter lines (42 and 31 characters) where a long code span
forces the break. **No line outside 64–71 moved** — everything from `and report `base.reason`.`
onward is byte-identical.

What the wording does, clause by clause:

- **"does nothing, and says nothing"** — both halves of the measurement above. The second half is
  the one a reader cannot discover for themselves: `claims --remote` with `claim_remote` empty
  exits 2 and names the key, so a user who passes it learns the key exists; `--fetch` is silent,
  so a user who passes it learns nothing (T097 *V5*). That asymmetry is the whole reason route C
  exists, and the skill is the only place an executor will meet it.
- **"unless the repository sets `[git].branch_record_remote`"** — the key is named in full, so the
  next reader can grep for it. The old "when the repository mirrors them" named nothing.
- **"without which a task … reads here as pending on a template name"** — the consequence when the
  key *is* set, in the executor's own terms. An executor that reads only "does nothing" might drop
  the flag from its own habit; this says why it must not.
- **The clause is split out of the em-dash sandwich into its own sentence**, which is what makes it
  hard to read past. `base.onto` then starts a new sentence, so the step's instruction survives
  intact.

### `README.md` — the decision the task leaves open

Line 82, in the command reference:

```
taskrail show T012 --json --fetch      # …after fetching branch names other clones recorded
```

Proposed:

```
taskrail show T012 --json --fetch      # …first fetching branch records, when [git].branch_record_remote is set
```

**Approved at the gate and applied.** It is a different
audience — a human skimming a cheat sheet, not an agent following an instruction — so it gets a
named condition and nothing more: no sentence about what breaks without it, which belongs in the
skill. Naming the key is exactly the difference between a reader who can look it up and one who
cannot, and it matches the flag's own `--help`
(`cli.py:1476`: *"first fetch branch records mirrored to `[git].branch_record_remote`"*), which
today is more informative than the README line teaching it. The block's own note says the examples
are "written short so they fit"; at 111 characters the new line stays inside the block's existing
width (line 91 is 139).

The alternative, leaving line 82 alone, is defensible — it is a comment, not a contract — but it
would leave the repository half-answered on a question T097 put in writing, and the next audit
would find the same sentence.

## Decisions

All three were put at the `scope` gate and answered there; none changes behaviour. Recorded in
`docs/autopilot/decisions/T104-state-in-the-core-skill-that-show-fetch.md`.

1. **The wording of the skill clause** — accepted, with the fragment fixed to *"Take `show`'s
   `base.onto` as the ref to branch from"*. The three properties the wording was chosen for stand:
   it names the key so it can be grepped, it states the **silence**, which is the half a user
   cannot discover, and it keeps the mirrored consumer's stake so an executor does not drop the
   flag from habit.
2. **`README.md`, the line teaching the same command** — same treatment, in the minimal form.
3. **The installed copies, shared with a lane editing the same file.** Another lane in this run is
   rewriting this file's frontmatter `description` and the prose on line 11, and runs
   `taskrail upgrade` as this task does, so both branches carry a regenerated
   `.claude/skills/taskrail/SKILL.md` and `.taskrail/installed.json`. Both lanes regenerate anyway,
   and the collision is resolved by re-running the generator after the source conflict is
   resolved. The reason it is safe is mechanical and general: `.taskrail/installed.json` is a map
   of **sha256 content hashes** — no timestamps, no ordering — and the installed skill is the
   source with `<!-- taskrail:harness -->` substituted, so both files are pure functions of the
   source tree and a conflict in them **carries no information that can be lost**. Skipping
   `taskrail upgrade` here was considered and rejected: it would leave this branch inconsistent
   with its own source in review, and it would only work if the other lane merged second, which no
   lane controls.
