# T120 — Give the generated GitHub workflow a least-privilege permissions block

Kind: chore · Epic: E05 · Depends on: — · Branch: `T120-give-the-generated-github-workflow-a-lea`

## Goal

The workflow template in `src/taskrail/install.py` (`workflow()`) sets no `permissions`, so in
every repository that installs `--github-workflow` the `validate` job runs with the repository's
default `GITHUB_TOKEN` permissions. In repositories created before GitHub changed the default,
and in any organisation that still sets it so, that default is **read-write on every scope** —
contents, issues, pull requests, packages, deployments — while the job only checks the repository
out and runs `taskrail validate`. This repository's own hand-written `.github/workflows/ci.yml`
already sets `permissions: contents: read`; the generated one should too.

Noticed by T117's lane reading the two workflows side by side, and opened as this task because
the fix belongs in the template, which T118 owned at the time.

## Change set

- `src/taskrail/install.py` — `workflow()` gains a workflow-level `permissions:` block with
  `contents: read`, between the `on:` block and `jobs:`, the same position and shape as `ci.yml`.
  Four lines of template text; no new parameter, flag or configuration (decision 1).
- `tests/test_install.py` — one new test beside `test_github_workflow_pins_every_action_to_an_exact_release_tag`,
  asserting the generated workflow grants the job only `contents: read` (decision 3).
- `.github/workflows/taskrail.yml` — regenerated by running this worktree's own
  `.taskrail/bin/taskrail upgrade`, so this repository's managed copy matches the template it
  ships (decision 2). Never hand-edited.
- `.taskrail/installed.json` — the `files` digest for that workflow, rewritten by the same
  `upgrade` run. Shared file, appended-only conflict class; a digest conflict is resolved by
  re-running `upgrade`, not by a textual merge.
- `DESIGN.md` §9 *Extras* — a clause in the existing `--github-workflow` sentence recording the
  convention (decision 4).
- `CHANGELOG.md` — one bullet under *Unreleased* (decision 4).
- `docs/chores/T120-…md` and `docs/chores/README.md` — this write-up and its index row.

The generated workflow becomes:

```yaml
# Managed by taskrail: `taskrail init --github-workflow` and `taskrail upgrade` rewrite this file.
name: taskrail

on:
  pull_request:
  push:
    branches: [main]

permissions:
  contents: read

jobs:
  validate:
    …
```

## Decisions needed

1. **Where the block goes and what it contains.** Recommendation: **workflow-level
   `permissions:` with the single scope `contents: read`**, exactly as the backlog row proposes,
   placed between `on:` and `jobs:`.
   Checked against what the job actually does: `actions/checkout` reads the repository (contents);
   `astral-sh/setup-uv` downloads a release of a *public* repository, which a read-scoped token
   reaches (token scopes bound the workflow's own repository, and public reads need no more);
   `.taskrail/bin/taskrail validate` reads the checkout and, for a non-`local:` pin, clones the
   public taskrail repository over anonymous HTTPS with no token at all. Nothing in the job
   writes anything back to the repository — no comment, no commit, no status, no artifact upload.
   So `contents: read` is sufficient, and naming one scope makes every unnamed scope `none`,
   which is the least-privilege result.
   Workflow-level rather than job-level because the file has one job, the two forms are then
   identical in effect, and workflow-level is the shape `ci.yml` already uses, so the two
   workflows in this repository read the same and a second job added to the template later
   inherits the restriction instead of silently getting the default. Alternatives: (a) job-level
   under `jobs.validate` — same effect today, diverges from `ci.yml`, and a future job would
   start unrestricted; (b) `permissions: {}` — no token scopes at all: checkout of a *private*
   repository would fail, and taskrail's consumers are often private, so this would break them;
   (c) leave it and document that consumers set it themselves — the row rejects this, and a
   default that is wrong in older repositories is not a consumer's job to discover.

2. **Whether this repository's own `.github/workflows/taskrail.yml` is regenerated here.**
   Recommendation: **yes, in this task, by running this worktree's `.taskrail/bin/taskrail
   upgrade`**, committing the regenerated workflow and the manifest digest that follows from it.
   The file is managed and currently unedited — its sha256 equals the digest in
   `.taskrail/installed.json` (evidence below) — so `upgrade` rewrites it without `--force` and
   this is exactly the pick-up path the change tells consumers to use. Leaving it stale would
   ship a generated file in this repository that does not match its own template, which is the
   argument T118 faced about the wrapper and answered by regenerating, and it would mean this
   repository's own `validate` job keeps running with the default permissions until some later,
   unrelated `upgrade`. The cost is two lines of diff in files this lane already touches.
   Alternative: leave it to a later `upgrade` — smaller diff, but the repository then dogfoods a
   copy it knows is out of date, and the next lane to run `upgrade` for its own reason picks up an
   unexplained workflow change.

3. **What the test asserts and where.** Recommendation: **one new test in `tests/test_install.py`
   directly after `test_github_workflow_pins_every_action_to_an_exact_release_tag`**, named
   `test_github_workflow_grants_the_job_only_read_access_to_contents`, asserting the literal
   block `\npermissions:\n  contents: read\n` in the generated file — the same style as
   `test_github_workflow_checks_out_full_history`, which asserts its literal `fetch-depth: 0`
   fragment.
   Literal rather than general because, unlike T116's tag test, there is nothing to generalise
   over: the assertion is about one block with one scope, and the shape *is* the content. A
   general form ("some `permissions` key exists") would pass for a block that grants
   `contents: write`, which is the failure the task exists to prevent. Alternatives: (a) parse
   the YAML and compare the mapping — the test suite has no YAML parser and taskrail has no
   runtime dependencies, so this would add one for one assertion; (b) extend T116's existing test
   — it is about action refs, and folding two unrelated invariants into one test makes a failure
   read wrongly.

4. **`DESIGN.md` §9 *Extras* and `CHANGELOG.md`.** Recommendation: **a clause in the existing
   *Extras* bullet and one `CHANGELOG.md` bullet; no `README.md` change.**
   §9's *Extras* bullet already records the two other properties of this template that a reader
   would otherwise change by accident — `fetch-depth: 0` and the exact release tags — each with
   its reason; the permissions block is the third of exactly that kind, so it belongs in the same
   sentence rather than in a new paragraph. The `CHANGELOG.md` bullet is warranted because the
   file consumers get changes and they pick it up with `taskrail upgrade` — the same situation as
   T116's bullet, and it is the only place a consumer with a locally edited workflow is told they
   must add the block themselves. `README.md`'s one-line description of the extra stays as it is:
   it says what the extra adds, not how the job is configured, and the permissions block does not
   change what a consumer runs or decides.

## Out of scope

- Any new flag, option or configuration key controlling the permissions block. The row asks for
  one fixed least-privilege block; CLAUDE.md's YAGNI and KISS rule out making it adjustable
  before anyone has asked for a different value.
- `.github/workflows/ci.yml` — hand-written, already correct, not this task's file.
- The wrapper template and `.taskrail/bin/taskrail` (T118's, already merged in this branch's
  base) and `src/taskrail/cli.py` and `DESIGN.md` §7 (T119's, unmerged).
- Anything else `upgrade` might rewrite: if the run touches a file outside the change set above,
  this lane stops and asks rather than committing it.
- Branch protection, required checks, or the repository's default `GITHUB_TOKEN` setting on
  GitHub — the human's, not a lane's.
- Other `permissions` scopes, `id-token`, or anything about a future job that would need to write.

## Documentation and follow-ups

- **`DESIGN.md` §9 *Extras***: the `--github-workflow` sentence already recorded the template's
  two other deliberate properties — `fetch-depth: 0` and the exact release tags — each with its
  reason. The permissions block is the third of the same kind, so it is a clause in that same
  sentence: `contents: read` at the workflow level and nothing else, because the job writes
  nothing back and every scope a `permissions` block leaves unnamed is `none`, against a default
  that is read-write in older repositories. Nothing else in §9 changed.
- **`CHANGELOG.md`**: one bullet under *Unreleased*, beside T116's bullet about this same
  template. It names what the default was, what the block is and why it is `contents: read`
  rather than no scopes at all, and it says plainly what `upgrade` cannot do for one consumer:
  a repository whose workflow was edited locally is left alone and reported as
  `edited locally; --force replaces it`, so it adds the two lines itself — the bullet prints them.
- **`README.md`** was not changed: its one line describes what the extra adds, not how the job is
  configured, and nothing a consumer runs or decides changes.
- No follow-up tasks. Nothing outside the change set needed touching, and no design principle in
  `CLAUDE.md` argued against what the row asked for — the change adds four lines of template text,
  no flag and no configuration.
