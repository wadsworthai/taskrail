# T129 — Cut releases with relscribe v0.1.0

Kind: chore · Epic: E10 · Status: scope

## Goal

Replace README's hand-run *Releasing* steps with [relscribe](https://github.com/wadsworthai/relscribe),
pinned as `uvx --from git+https://github.com/wadsworthai/relscribe@v0.1.0`: relscribe computes
the next version from the Conventional Commits on `main`, writes it together with `uv.lock`, the
version pins in the docs and `CHANGELOG.md` in one release commit, and a workflow tags the squash
commit when it lands on `main`.

Decided with the human before this scope was written:

1. **`main` carries no `.dev0` version any more.** relscribe accepts only plain `X.Y.Z`
   (`relscribe status` today: `pyproject.toml: version '0.5.0.dev0' is not a plain X.Y.Z version`).
   `main` goes back to `0.4.0`, the last release, and README's step 3 no longer bumps it. What this
   gives up: a CLI installed from a commit of `main` reports `0.4.0` and the wrapper pinned to
   `v0.4.0` accepts it. The recommended route — `uvx` from the tag — is not affected.
2. **`CHANGELOG.md` is generated by relscribe** from the squash commits' subjects, in Keep a
   Changelog form, from the next release on. Nobody writes entries by hand; the curated sections of
   0.1.0–0.4.0 stay as they are.
3. **Tags are created by CI** (`release.yml`, `relscribe tag <before>..<after> --push origin` on
   every push to `main`). Merging the release pull request is the approval.
4. **Pull request titles are linted** by `relscribe lint` in CI (`pr-title.yml`).

## Decisions needed

**A. relscribe v0.1.0 cannot tag cleanly on the first pushes after this change.** Reproduced in a
scratch clone of `main` with this change set applied as one commit (`5a2c3f1` below):

```
$ relscribe status
taskrail (.): 0.4.0, no release
  base: tag v0.4.0 (a0994e3)

$ relscribe tag --dry-run HEAD^..HEAD          # the push that merges this pull request
relscribe: 62c7edf: pyproject.toml: version '0.5.0.dev0' is not a plain X.Y.Z version   (exit 2)

$ relscribe tag --dry-run HEAD^..HEAD          # any later push to main, before the next release
conflict v0.4.0 5a2c3f1: already on a0994e3 (reconciled)                              (exit 4)
```

`tag` takes the commit that sets `0.4.0` as the latest 0.4.0 release, finds it untagged, and
reconciles it into `v0.4.0`, which already sits on `a0994e3`. The conflict ends with the next
release — simulated with a `fix` commit and `relscribe release --commit`:

```
$ relscribe tag "$BEFORE..HEAD" --push <remote>
conflict v0.4.0 5a2c3f1: already on a0994e3 (reconciled)
created v0.4.1 cfe4333
pushed 1 tag to <remote>                                                               (exit 4)
$ relscribe tag --dry-run HEAD..HEAD
existing v0.4.1 cfe4333 (reconciled)                                                   (exit 0)
```

Options:

- **A1 — fix it in relscribe first, then pin that release here.** Reconcile should not treat a
  commit as a release when its version is already tagged on an ancestor (and range mode should not
  fail on a non-plain parent). `main` stays green throughout; the pin becomes `v0.1.1` or whatever
  relscribe releases, not `v0.1.0`.
- **A2 — `v0.1.0` now, `release.yml` now.** The merge's run fails (exit 2) and every push to `main`
  fails the tag job (exit 4) until the next release, whose run creates and pushes its tag and
  clears it.
- **A3 — `v0.1.0` now, `release.yml` added by the next release's pull request.** `main` stays
  green until then; that release's run creates and pushes the tag but exits 4 once.

**B. Keep the version pins in README and DESIGN under `sync`?** Recommended: yes — T127 edited
them by hand; `sync` does it in the release commit and fails the release if one drifts.
Alternative: leave them manual in the Releasing steps.

## Out of scope

- Rewriting or regenerating the existing 0.1.0–0.4.0 changelog sections.
- Cutting a release: the next version is released by its own task.
- `exclude` globs (for example tests or `TODO.md`): no commit type that bumps is used today for
  a backlog- or test-only change.
- Changing how the wrapper matches `taskrail --version` against the pin (decision 1 accepts it).
- Repository settings on GitHub; the README lists them, a maintainer applies them.

## Verification

- `relscribe status` exits 0 and reports base `tag v0.4.0 (a0994e3)`, no release.
- `relscribe release --commit` in a scratch clone after a `fix` commit writes `pyproject.toml`,
  `uv.lock`, the synced README/DESIGN lines and a `## [0.4.1] - <date>` section under
  `## [Unreleased]`, and `uv run --locked pytest` still passes on that commit.
- `relscribe lint` accepts this pull request's title and rejects a non-conventional one.
- `relscribe tag --dry-run` behaves as decision A says for the chosen option.
- `uv run pytest -q` passes; `.taskrail/bin/taskrail validate` passes.
- The workflows are checked with `actionlint` if available; otherwise by their runs on this
  pull request (`pr-title`) and after the merge (`release`).
